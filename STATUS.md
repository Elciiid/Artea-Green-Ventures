## Addendum: excessive vertical spacing fix (2026-07-30)
**Reported bug:** a large empty gap between the top nav and actual page content on `/admin/people/roles`, forcing scrolling to reach the Role assignment form.

**Actual source:** not the People layout itself — one level up, in `AppShell.tsx`'s shared `<main>` element, which has had `justify-content: center` since the very first scaffold commit. This vertically centers every page's content within the full flex space between header and footer; on short-content pages at tall viewports, that pushes content down by whatever space is "left over." Confirmed via live `getBoundingClientRect()`/computed-style checks (Browser pane screenshots weren't exercised this pass, so the DOM-measurement route was used throughout): toggling `justify-content` to `flex-start` live in the browser collapsed the gap from 207px to exactly the intended `py-12` padding (48px).

**What changed:** removed `justify-center` from `AppShell.tsx`'s `<main>` className (one class, no new spacing values introduced — same `py-12` padding as before, just no longer fighting a centering rule on top of it).

**Where else it showed up:** the same root cause affects every page through the shared shell, not just People — measured at 1920×1080 before the fix:
- `/admin/people/roles` — 207px gap (bug)
- `/admin` (Applications Register) — 217px gap (bug, only 3 seed rows)
- `/home` — 198px gap (bug)
- `/admin/people/access`, `/admin/people/activity`, `/account` — no visible bug; each page's own content already fills or exceeds the available space, leaving nothing for centering to redistribute

Fixing `/home` too was a real fork (Home's centered feel was arguably intentional for a landing page), raised with the user explicitly — chosen to fix everywhere for consistency rather than special-case Home. All three People tabs and `/admin`/`/home` re-verified clean (48px gap, primary content visible without scrolling) at both 1920×1080 and 1440×768; `/account` unchanged (was already fine). Commit: 6263e77.

A follow-up instruction then asked to revert Home's centering specifically (its "landing page" feel was worth keeping after all) without reopening the general fix. Handled via an opt-in `centerContent` prop on `AppShell` (default off), set only on `/home/page.tsx` — the other pages stay top-aligned. Commit: 1093b47.

## Addendum: People pages — bounded shell, pagination/filter, and a sticky-header bug (2026-07-30/31)
Follow-up to the two fixes above: even with the redundant headings gone, the Access and Activity tabs' content lists render unbounded in normal page flow, so a list with enough rows still pushes the footer out of reach. Three things changed:

**1. Bounded shell (header/nav/tabs pinned, footer always visible).** `AppShell` gained a `boundedContent` prop: instead of `min-h-dvh` (grows with content), the shell becomes `h-full` inside a viewport-bounded parent, with `header`/`footer` as `shrink-0` flex items and `<main>` as `flex-1 min-h-0` — pure flex distribution, no hardcoded pixel heights. `src/app/admin/people/layout.tsx` passes `boundedContent` and gives its own heading/tab-nav `shrink-0` and the tab content `min-h-0 flex-1`, so each tab is responsible for its own internal scroll region.

**2. A real bug this surfaced: `DemoBanner` overflowed the bounded shell.** `DemoBanner` renders in root `layout.tsx` as a sibling *before* `AppShell` — outside its `h-dvh` calculation — so on a `boundedContent` page the shell claimed the full viewport height *underneath* the banner, overflowing the page by exactly the banner's height (29px, confirmed via `getBoundingClientRect()` at 1920×1080). Fixed by wrapping `DemoBanner` and the page content together in one `flex h-dvh flex-col` container in root `layout.tsx` (banner `shrink-0`, content `flex-1 min-h-0 overflow-y-auto`), and changing `AppShell`'s `boundedContent` height from `h-dvh` to `h-full` so it fills whatever the true parent leaves after the banner, instead of independently re-claiming the whole viewport. Re-verified: `documentScrollHeight` now matches `windowInnerHeight` exactly, footer fully visible, at both 1920×1080 and 1366×768, on all three People tabs. Roles was checked too and deliberately left unbounded — its content is short and stretching it to fill the flex space isn't needed; confirmed it still renders at its natural height with the footer unaffected.

**3. Pagination + filter, and a genuine sticky-header bug caught during verification.** Added a shared `SimplePagination` component (`src/components/admin/SimplePagination.tsx`, Previous/Next + "Page X of Y", 5 rows/page) and a name/role filter `Input` to `AccessMatrix`, and pagination to both of `ActivityLog`'s sub-tabs. While verifying the sticky table header on Access (bg-pine header row that should stay pinned while the row list scrolls), found it didn't stick at all — traced to two stacked causes, confirmed empirically by toggling each live rather than guessed:
  - Motion's own entrance-animation `transform` on the scrolling `motion.section` breaks `position:sticky` for its descendants, even once fully settled to an identity `translateY(0)` (not just mid-animation) — fixed by never letting the Motion-animated element also be the scroll container.
  - Separately, shadcn's shared `Table` primitive already wraps `<table>` in its own `data-slot="table-container"` div with `overflow-x-auto`; per the CSS overflow spec that silently forces `overflow-y` to compute as `auto` too, but since that div has no explicit height it can never actually scroll — so `position:sticky` locks onto it as the "nearest scrolling ancestor" without it ever scrolling, and the header just rides along with the page. Fixed by giving that existing container `h-full` (via an arbitrary Tailwind selector on `AccessMatrix`'s wrapping `motion.section`, since `Table` doesn't expose a container className prop) rather than adding a redundant second scroll box. Re-verified live: header stays pinned through a genuine scroll (`scrollTop` changed, header position unchanged), on a real dataset with actual overflow (8 profiles/2 pages on Access; the audit log's "In-app activity" sub-tab has 7 real pages, a good stress case). This is a new entry for the running "shadcn default silently breaks under composition" hazard family — distinct from the padding/border/text-label cases already on record. `ApplicationRegister.tsx` also uses the shared `Table` but has no sticky header and isn't inside a bounded shell, so it isn't affected.

**Verified:** footer visibility and no page-level overflow at 1920×1080 and 1366×768 on Roles/Access/Activity; Access's filter narrows results correctly and resets to page 1; keyboard Tab order through filter → row checkboxes → Previous/Next is correct and reaches every control (confirmed via the accessibility tree, not assumed) with no keyboard trap; all pagination/filter controls have distinct, correct accessible names; both Activity sub-tabs paginate correctly on a real (non-synthetic) dataset. One environment limitation hit during this pass, not an app bug: this session's Browser-pane automation cannot dispatch a synthetic Enter/Space keypress that activates a focused native `<button>`/`<a>` element (confirmed on three unrelated elements — a pagination button, a dropdown trigger, a nav link — real mouse clicks work correctly on all of them). Keyboard *reachability* was verified directly; keyboard *activation* of already-standard, unmodified native elements should be assumed fine but wasn't independently provable in this tooling.

**Not done:** the Roles page's person-select dropdown was separately reported as rendering detached from its trigger. Reproduction was attempted extensively (multiple viewports, selection states, hard reload) and did not reproduce in this environment; one apparent lead (resize-while-open) was confirmed to be a tool artifact (this session's `resize_window` doesn't dispatch a real `window.resize` event) rather than a genuine repro. Still open, blocked on a real screenshot or more precise repro steps from the user.

## Addendum: header shift between Home and People, and a starved Access list (2026-07-31)
**Reported bug:** navigating from Home to the People section visibly shifts the top nav (account pill/avatar) a little to the right. Confirmed with two screenshots showing the avatar sitting further right on People than on Home.

**Root cause:** `AppShell.tsx`'s non-bounded shell used `min-h-dvh` — an absolute viewport unit that ignores how much height its flex parent actually allocated to it. That parent's real available height is already viewport-minus-`DemoBanner`, so `min-h-dvh` silently overflowed it by exactly DemoBanner's height (~29px) on every non-bounded page, forcing a permanent ~15px scrollbar that isn't there on `boundedContent` pages (which already use `h-full` for the same reason, fixed in an earlier pass). Home has that scrollbar; People (bounded) doesn't — the scrollbar appearing/disappearing between the two is exactly the shift. Confirmed live: on Home, the outer scroll container measured `clientWidth 1265` vs `offsetWidth 1280` (scrollbar present) and the avatar sat at `right: 1241`; on People, `1280/1280` (no scrollbar) and the avatar sat at `right: 1256` — a 15px difference matching the screenshots exactly.

**Fix:** `min-h-dvh` → `min-h-full` on the non-bounded path. `min-h-full` correctly floors at "whatever height the parent actually gave me" (properly accounting for DemoBanner) while still letting genuinely long pages (e.g. Applications Register) grow taller than that and scroll normally — re-verified `/admin` still shows its real scrollbar (`scrollHeight 742 > clientHeight 691`) and its footer still requires scrolling to reach, exactly as before. After the fix, Home's avatar position (`right: 1256`) now matches People's exactly, and a live Home→People navigation shows the avatar at the identical pixel position before and after.

**Also found and fixed along the way:** while reproducing the above, found that the Access tab's row list was starved to less than one row's visible height (`clientHeight` as low as 74–94px) at common laptop viewport heights, because `boundedContent` pages still carried the same `py-12` (48px top+bottom) padding as regular pages. Reduced to `py-6` specifically for `boundedContent` (non-bounded pages unchanged, confirmed still `48px/48px` on Home) — recovers real space for the list (confirmed `clientHeight` 94→142px) without affecting the pinned-footer/no-page-scroll behavior.

Both fixes: `tsc --noEmit` and `npm run lint` clean. Not yet committed.

## Addendum: senior front-end review + fixes for the top 5 findings + a security bug (2026-08-01)

A full critical front-end review was run against the committed state of `main` (`FRONTEND_REVIEW.md`, repo root — not gitignored, meant to live as real documentation alongside this file). Six items from it were fixed on an isolated branch/worktree (`review-fixes`, `.worktrees/review-fixes/`), executed via `superpowers:subagent-driven-development` — a fresh implementer subagent per task, a task-scoped reviewer after each (two of which triggered real fix-and-re-review loops), and a final whole-branch review at the end. **Nothing from this branch has been merged to `main` or pushed** — it's sitting on `review-fixes` pending your review, same as everything else in this file marked "not yet committed"/"nothing pushed."

**1 — `--color-ash` WCAG AA contrast failure.** `#6b7264` → `#686e61` in `globals.css`'s `@theme` block (one token, ~40 call sites inherit it). Independently recomputed by two different reviewers using the full sRGB→linear→relative-luminance formula (not trusted from the original review): **4.72:1** against `--color-void`, **5.03:1** against the composited `.glass` background — both clear the 4.5:1 AA floor. (The first implementer pass miscalculated the gamma-correction step and reported failing numbers as a false "PASS" — caught and corrected in the report before this was accepted; the shipped color value was correct throughout.)

**2 — `revokeAccess()` was the one unguarded write in the codebase.** `src/lib/supabase/access.ts` now selects the row back and calls the existing `assertRowReturned()` guard (same pattern as `applications.ts`/`documents.ts`), so a revoke that RLS silently no-ops on now throws and surfaces the existing `toast.error` in `AccessMatrix.tsx` instead of the checkbox quietly reverting with no explanation.

**3 — Three different loading/error/empty-state contracts across Directory/Access/Activity.** Built one `useAsyncResource<T>()` hook (`src/lib/useAsyncResource.ts`) and one `<SurfaceState>` component (`src/components/SurfaceState.tsx`) — a behavioral wrapper, not a redesign — and migrated `PersonDirectory`, `AccessMatrix`, `ActivityLog`, `AdminDashboard`, and `UserPortalView` onto them. Fixed the four bugs this was chasing: Access's literal `No one matches "".` on an empty unfiltered list (now distinguishes filtered-empty from truly-empty); `AdminDashboard` had no empty state at all (now has one); `ActivityLog` swallowed a failed profile-name lookup silently (now shows a visible `role="alert"` notice instead of just falling back to raw UUIDs); none of the three had `role="alert"` on their error text (baked into `SurfaceState` now, so no surface can omit it again). `RegisterStatus.tsx` is fully deleted (zero remaining references). A task review caught that the migration had silently dropped the `<h2>` heading above error messages on three surfaces (a real, if narrow, UX regression) — restored via an `errorHeading` prop on the three surfaces that had one.

**4 — `RoleChangeDialog` never pre-selected the current role, and (this took two passes to actually fix) wiped the selection on a failed save.** The dialog is opened externally (`open={editing !== null}`, no `DialogTrigger`), so Radix never calls `onOpenChange` on that transition — added a `useEffect` keyed on `[open, person]` to pre-select correctly regardless of how the dialog was opened. The "preserve selection on failure" half of the fix was applied but didn't actually work at first: `PersonDirectory`'s `handleRoleChange` catches its own errors and never rethrows, so the dialog's `await onConfirm(...)` always resolves — meaning the "only clear on success" logic always ran, "success" or not. Only caught by the **final whole-branch review**, which had both files open side by side (something no single task's reviewer could see) — fixed by simply deleting the explicit reset, since a real success already unmounts the dialog via `setEditing(null)`, and the pre-select effect reseeds fresh next time it opens regardless.

**5 — No `eslint-plugin-react-hooks`, and no automated tests at all.** Added the plugin (pinned to 5.2.0, not the "latest" 7.x tag, to avoid pulling in the React Compiler linter's ~15 unrelated strict rules) — it immediately confirmed two real live bugs it exists to catch: `AppShell.tsx` was recreating its `allowedRoles` array every render (any caller passing a bare-string `expect` prop, e.g. `people/layout.tsx`'s `expect="admin"`, caused its route-guard effect to re-run on every render), fixed with `useMemo`; `PersonDirectory.tsx`'s `load()` wasn't listed in its own effect's deps, fixed with `useCallback` (later superseded cleanly by Task 3's `useAsyncResource` migration, which replaced it with that hook's own `refetch`). Separately established this repo's first-ever test infrastructure (Vitest + jsdom + React Testing Library, zero prior setup existed) and one integration test for `AccessMatrix`'s grant/revoke round-trip — including a deliberate-breakage sanity check (commented out the real `revokeAccess()` call, confirmed the corresponding tests actually failed, then reverted) to prove the tests aren't vacuous.

**6 — Security-critical: a sole admin had no floor against self-demoting.** `POST /api/admin/set-role` writes with the service-role client (bypassing RLS and the `agv_prevent_self_role_escalation` trigger entirely, since that trigger only blocks escalation and can't see service-role writes at all), and had no check comparing the target `profileId` against the caller's own id — a sole admin changing their own role to `staff`/`client` through the Directory UI would lock the whole org out of `/admin` with no self-service recovery. Fixed server-side (not just hidden in the UI) with a `profileId === user.id` rejection placed before the write. **A security-focused task review then found this first pass was itself bypassable**: the guard used JS `===` while the actual database write resolves via Postgres's looser `uuid`-type equality — so an admin calling the route directly (not through the UI) with a non-canonical rendering of their own id (uppercase, hyphens omitted, or wrapped in braces) could slip past the `===` check while Postgres still matched it as the same row, completing the self-targeted write anyway. Closed with a strict canonical-UUID format check plus a case-insensitive comparison (both halves required — either alone leaves a gap). Re-reviewed and independently stress-tested against 20+ bypass shapes (case variants, hyphen/brace stripping, whitespace, null bytes, Unicode lookalikes, regex-anchor edge cases) with none succeeding, and confirmed normal admin-to-admin role changes are unaffected. As a UX nicety only (explicitly not a substitute for the server check), an admin's own card in the Directory no longer opens the role-change dialog at all.

**Verified across the whole branch:** `npx tsc --noEmit`, `npm run lint`, `npm test` (3/3), and a full `npm run build` (20 routes) all clean at the final commit. No dev server / live Supabase connection was available in this environment for any task, so UI-rendering and RLS-rejection claims are verified by rigorous code tracing rather than a real browser — flagged honestly at every step rather than claimed as live-tested.

## Decisions made
- Each slice gets its own plan written only when that slice starts, not all up front (roadmap decision, reaffirmed each slice).
- Kokonut's own branded registry components are evaluated case by case and rejected when they're demo compositions rather than generic primitives — happened in Slice 1.
- Recurring "shadcn base class silently survives `cn()` merge" bugs are now the reason for the standing rule: after any `npx shadcn add`, diff the fetched file against its override call sites before assuming an override works. Two more mechanisms in this family surfaced in Slice 5 (Radix `Slot`'s plain-string className merge; unlayered project CSS beating Tailwind utilities).
- The admin IA change (a "People" nav entry replacing "User access", with three tabbed sub-routes) was confirmed explicitly with the user before Slice 5's plan was written, since the roadmap flagged it as its own decision.
- The domain `portal.arteagreenventures.com` is a subdomain (not the root domain), configured via a CNAME in Wix pointing at the existing Vercel project — the root domain stays free for a separate marketing site if one is ever built.
